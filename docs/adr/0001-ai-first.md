# ADR 0001：AI 友好是一等架构约束

- **状态：** 已接受
- **日期：** 2026-10-19
- **决策者：** 项目维护者

## 背景

DAW 的操作面很大：轨道、片段、设备、节点、自动化、渲染。如果 AI 只能靠截图和模拟鼠标来操作，成本高、易错、不可验证，而且每次 UI 改版都会失效。

MCP 只是传输层。真正决定 AI 能不能干活的，是引擎是否具备下面这些性质。把它们写进架构，MCP 就只是一个薄适配器；反过来先做 MCP 再补架构，只会得到一个浅层 API。

## 决定

### 1. 引擎无头化

所有能力都不依赖 UI。`aurtrack-cli` 是第一个客户端，不是附属工具。

### 2. 命令注册表是唯一事实来源

每个命令声明：

- 稳定 ID（例如 `track.create`）
- 参数 JSON Schema
- 前置条件与权限
- 撤销语义（逆操作 / 快照 / 不可撤销）
- 一句中文说明

CLI、会话协议、MCP 工具、参考文档、测试，全部从注册表生成。禁止手写第二套接口。

### 3. 一切可寻址

每个实体有稳定 ID 和路径，例如 `/tracks/bass/devices/0/params/cutoff`。支持按路径 `get` / `set`，不要求调用方遍历整棵树。

### 4. 一切可内省

`describe` 返回机器可读的能力清单：命令、节点类型、参数、单位、范围、延迟、版本。AI 不需要读文档就能发现能力。

### 5. 一切可验证

渲染必须确定性。提供分析工具：响度（LUFS）、频谱摘要、峰值、两次渲染的空测试对比。没有验证手段，agent 只能盲写。

### 6. 一切可回滚

多步编辑走事务；破坏性命令支持 `dry_run`；撤销历史可查询。agent 犯错时，代价应该是零。

### 7. 输出省 token

默认返回摘要，支持字段选择、分页、游标和 diff。禁止把整个工程、整段波形或 base64 音频塞进返回值；音频只返回路径和元数据。

### 8. MCP 是适配器

`aurtrack-mcp` 只做「协议消息 ↔ MCP tool」的映射，不写业务逻辑，不持有状态，不绕过命令注册表。

## 后果

**正面**

- AI 与脚本共用一套 API，不会出现「脚本能做的 AI 不能做」。
- CLI 天然可测，CI 可以跑完整工作流。
- 文档、类型、工具描述都从同一处生成，不会漂移。
- 将来换 agent 协议只需要再写一个适配器。

**负面**

- 命令注册表必须提前设计，初期开发会慢一点。
- 每个命令都要补 schema、撤销和测试，不能只写「能用」。
- 内省和 token 预算需要持续投入，不是一次性的。
