# 0028 固定 64 帧累加器快路径的评估

## 状态

已评估并拒绝（2026-11-13）。临时原型在 128 同时音符上没有可测收益：
三次中位数 678.6ms → 682.6ms（+0.6%，在计时噪声内），远低于 10% 的
采纳门槛。生产代码保持 ADR 0027 的状态不变，不引入固定 64 帧特化。

## 背景

ADR 0026 把帧不变值从 64 元素数组改成标量广播，ADR 0027 又把
`sin`/`exp` 与帧循环算术换成 AVX2 + FMA 四路内核。128 同时音符的
2 秒离线渲染从约 1.5 秒降到 0.68–0.71 秒，但帧循环仍以运行期
`frames` 参数驱动：scratch 数组本来就是 `[f64; 64]`，所有帧循环却
通过 `[..frames]` 取切片，循环长度由参数决定。

ADR 0026 曾把“固定 64 长度的特化”列为下一步。本轮假设是：当
`frames == 64` 时，用无运行期长度参数的专用实例，LLVM 就能把帧循环
展开或向量化得更好，从而把 128 同时再压低 10% 以上。评估只在收益
明确时保留实现，不为默认 block 长度而特化。

评估时的基线（AMD Ryzen 9 8945H、Windows x86_64、release、48kHz、
64 帧 block、2 秒离线渲染）：

| 场景 | 三次测量（ms） | 中位数 |
| --- | --- | --- |
| 32 同时 | 182.8 / 179.7 / 181.2 | 181.2 |
| 64 同时 | 345.7 / 370.5 / 350.5 | 350.5 |
| 128 同时 | 685.1 / 678.6 / 665.9 | 678.6 |
| 300 顺序 | 327.0 / 310.5 / 336.2 | 327.0 |

## 原型

临时改动（未提交，评估后已还原）：

- `accumulate` 只做一次分派：`frames == 64` 走
  `accumulate_impl::<64>`，其余长度走 `accumulate_impl::<0>`；
- 固定实例里把帧数写成编译期常量 `64`，之后所有 `[..frames]`
  切片都与 `[f64; 64]` 等长，热路径不再有运行期长度参数；
- 调用方、短块/尾部路径、block ABI 都未改动。

概念上就是：

```rust
if frames == 64 {
    self.accumulate_impl::<64>(context, inputs, frames, count, carried, output)
} else {
    self.accumulate_impl::<0>(context, inputs, frames, count, carried, output)
}
```

并在 `accumulate_impl` 内用常量覆盖传入的 `frames`。改完跑同一个
`polyphony_stress_benchmark`，前后各三次：

| 场景 | 改动前中位数 | 改动后三次（ms） | 改动后中位数 | 变化 |
| --- | --- | --- | --- | --- |
| 32 同时 | 181.2ms | 187.8 / 180.0 / 174.8 | 180.0ms | −0.7% |
| 64 同时 | 350.5ms | 334.5 / 352.7 / 348.4 | 348.4ms | −0.6% |
| 128 同时 | 678.6ms | 714.6 / 670.9 / 682.6 | 682.6ms | +0.6% |
| 300 顺序 | 327.0ms | 325.1 / 339.0 / 351.9 | 339.0ms | +3.7% |

128 同时的实时系数从 0.333–0.343 变成 0.335–0.357；所有变化都在
±3% 的调度噪声内，没有一项达到 10%。300 顺序的 +3.7% 也落在噪声
与代码布局波动的范围内，不能算退化，但同样不是收益。

## 为什么没有收益

### 累加器的占比

用临时计时探针测了一次 128 同时：112896 次 `accumulate` 调用累计
585.8ms，整次渲染 759.7ms，约占 77%。探针本身让总时长从约 0.68 秒
升到约 0.76 秒，所以这个比例只是量级参考；它说明要让整次渲染快
10%，累加器自身必须快约 13%，不存在“小修小补”的空间。

### 反汇编证据

用 `cargo rustc --release -p aurtrack-engine --lib -- --emit=asm`
检查两个 `accumulate_impl` 实例（rustc 1.88，x86_64）：

- 分派确实是 `cmpq $64, %r9`，两个单态实例都生成了；
- 两个实例都有且只有 9 个 AVX2 内核调用点：`sin_slice`、`exp_slice`、
  `binary_slice`、`abs_slice`、`clamp_scalar_slice`、`sine_scalar_slice`、
  `sine_scalar_phase_slice`、`add_assign_slice`、`narrow_slice`；
- 固定实例没有内联或展开这 9 个内核，调用点数量与通用实例完全相同；
- 边界检查点从 134 个降到 125 个，减少的正好是固定 64 后不再需要的
  切片检查；标量后备循环没有被额外展开。

原因在 ADR 0027 已经记录过：这些 AVX2 内核是带
`#[target_feature(enable = "avx2,fma")]` 的独立函数，调用者没有该
特性，不能内联；内核内部的 `while index + 4 <= len` 仍按运行期长度
循环。固定 64 只能让外层少几次切片检查，碰不到内核的热循环。

固定实例确实完成了常量折叠，但 LLVM 的判断是不值得把 64 次迭代
全部展开；所谓“固定长度会触发自动展开”的假设在真实代码上不成立。

### 真正展开要付出的代价

要让内核按 64 展开，必须把整个解释器复制进 AVX2 `target_feature`
上下文，并为每个帧内核提供内联的固定长度变体：等于同时维护通用
解释器和 AVX2 解释器两套代码，再加 9 份专用内核。这已经超过“代码
复杂度可控”的边界，而且从上面的数据看，收益上限也没有把握达到
10%。用大量重复代码换一个不确定的小收益，不符合本轮的采纳标准。

## 决定

拒绝固定 64 帧快路径，不提交实现。理由按优先级：

1. 128 同时音符没有达到 10% 提升：中位数 +0.6%，与噪声不可区分；
2. 热路径是 9 个不可内联的 AVX2 内核调用，固定帧数改变不了它们；
3. 可行的深层版本需要复制整个解释器并为每个内核生成固定长度变体，
   代码量与维护成本不可接受，收益也不确定；
4. 快路径只对恰好 64 帧生效，却不改变 ABI；一旦默认 block 长度变化
   就会变成死代码，属于为默认值特化。

短块、尾部、seek/stop、零分配与 block/scalar 容差语义都未受影响，
因为生产代码没有改动。`AURTRACK_SIMD=0` 的标量回退仍是原有实现。

## 后续方向

- 继续压低 128 同时，应减少“每个 SSA 值一次分派、每个值一次 AVX2
  内核调用”的固定开销，例如把整个 body 编成更长的 SIMD 内核；这需要
  新的 IR 或代码生成层，不是固定 64 能解决的。
- 跨块缓存 `scalar_mask` 与标量求值结果（ADR 0026 已提到）仍是一个
  独立方向，但会引入新的状态与 seek/混合起始语义，需单独立项。
- AVX2 内核自身的循环展开可以作为独立微优化评估；它对所有帧数生效，
  不应绑定到 64，也不该以“固定 64 快路径”的名义引入。

## 复现

```sh
cargo test --release -p aurtrack-session --test block_realtime \
  polyphony_stress_benchmark -- --ignored --nocapture
AURTRACK_SIMD=0 cargo test --release -p aurtrack-session \
  --test block_realtime polyphony_stress_benchmark -- --ignored --nocapture
```

原型不在仓库中；按“原型”一节的 `accumulate_impl::<64>` 分派即可在
十分钟内重建。反汇编检查：

```sh
cargo rustc --release -p aurtrack-engine --lib -- --emit=asm
```
